# Методология тестирования стратегии

**Пошаговый протокол валидации торговой стратегии с точки зрения
профессионального алготрейдинга — на полном функционале этого проекта.**

Документ отвечает на вопрос: *«В каком порядке и какими инструментами
проекта прогонять стратегию, чтобы отличить реальное преимущество от
артефакта подгонки под историю?»*

Главный принцип всей методологии: **каждый следующий шаг — это всё более
жёсткий фильтр против переобучения.** Хорошие цифры на ранних шагах не
значат ничего, пока стратегия не прошла поздние. Большинство «прибыльных»
стратегий умирает на шагах 6–9 — и это нормально, в этом и смысл.

Порядок шагов нарушать нельзя: нет смысла оптимизировать (шаг 4) стратегию,
которая заглядывает в будущее (шаг 2); нет смысла гонять Walk-Forward
(шаг 7) до проверки честности движка (шаг 1).

---

## Карта конвейера

```
0. ГИПОТЕЗА          сначала идея и экономический смысл, потом код
        │
1. ДАННЫЕ + ДВИЖОК   data_loader (качество) + sanity_check (честность ядра)
        │
2. ПРИЧИННОСТЬ        assert_no_lookahead + pytest — нет ли заглядывания в будущее
        │
3. ОДИНОЧНЫЙ БЭКТЕСТ  реалистичные издержки → метрики (читаем правильно)
        │
4. ОПТИМИЗАЦИЯ (IS)   Grid / Genetic, параллельно по ядрам
        │
5. ЛАНДШАФТ           тепловая карта + гистограмма: плато или одинокий пик?
        │
6. DATA SNOOPING      DSR, плато-выбор, permutation-тест, PBO/CSCV
        │
7. WALK-FORWARD        WFE на не виденных данных + purge + warmup
        │
8. МАТРИЧНЫЙ WFO       устойчивость к выбору длин окон IS/OOS (плато)
        │
9. МОНТЕ-КАРЛО         распределение исходов, риск разорения, план капитала
        │
10. РЕШЕНИЕ            go / no-go по чек-листу
```

## Шаг 0. Гипотеза прежде кода

**Зачем.** Профессиональная разработка начинается не с перебора индикаторов,
а с гипотезы о *причине* неэффективности рынка (микроструктура, поведенческий
паттерн, премия за риск, календарный эффект). Если экономического смысла нет,
любой хороший бэктест — это data mining: вы найдёте паттерн в шуме просто
потому, что перебрали много вариантов.

**Что сделать.**
- Сформулируйте гипотезу одним предложением: *«почему это должно работать и
  почему преимущество ещё не арбитражировано»*.
- Зафиксируйте заранее: инструмент, таймфрейм, тип стратегии (тренд/контртренд/
  возврат к среднему), ожидаемую частоту сделок, логику входа/выхода и риск.
- Решите **до** тестов, какой результат считать успехом (целевой Sharpe, макс.
  просадку, минимальный WFE) — иначе подгоните критерий под результат.

**Инструмент проекта.** Откройте `AI_STRATEGY_RULES.md` — это контракт и
чек-лист фреймворка: он помогает формализовать гипотезу под контракт проекта
и заранее держать в голове риски переобучения.

> ⚠️ Без этого шага все последующие проверки — лишь способ убедительно
> обмануть себя.

## Шаг 1. Данные и честность движка

Перед тестом стратегии нужно доверять (а) данным и (б) симулятору. Это
фундамент: ошибка здесь делает бессмысленным всё остальное.

### 1а. Качество данных — `data_loader`

**Зачем.** «Мусор на входе — мусор на выходе». Дубликаты баров, разрывы
(пропущенные сессии), нулевые объёмы и аномальные свечи искажают метрики и
могут создать ложное преимущество.

**Что сделать.**
- Загрузите свой CSV (понимает экспорт MT5: `<DATE>`, `<TIME>`, `<OPEN>`...):
  ```python
  from backtester import DataLoader
  df = DataLoader().load_csv("path/to/data.csv")
  print(loader.last_report)   # DataValidationReport
  ```
  В GUI — кнопка «Открыть CSV...». **Прочитайте отчёт валидации**: сколько
  строк загружено, сколько удалено дубликатов, есть ли разрывы в данных.
- Убедитесь, что период покрывает **разные рыночные режимы** (тренд вверх/вниз,
  флэт, кризис/волатильность). Стратегия, протестированная только на бычьем
  рынке, ничего не доказывает.
- Данные должны быть достаточно длинными для статистики: десятки-сотни сделок
  минимум, иначе метрики недостоверны (см. MinTRL на шаге 6).

### 1б. Честность ядра — `sanity_check.py`

**Зачем.** Прежде чем верить прибыли, убедитесь, что движок не «рисует» и не
«теряет» деньги и не заглядывает в будущее на уровне исполнения.

**Что сделать.**
```bash
python sanity_check.py
```
Скрипт проверяет 5 вещей: (1) сходимость баланса (сумма PnL сделок = изменение
счёта), (2) пустая стратегия = 0 сделок и ровная эквити, (3) без издержек
прибыль выше, чем с ними, (4) SL/TP исполняются по своим уровням, (5)
воспроизводимость (два прогона совпадают до копейки). **Все пять должны быть
`OK`.**

## Шаг 2. Причинность: нет заглядывания в будущее

**Зачем.** Lookahead bias — причина №1 фантастических бэктестов, которые
рассыпаются в реале. Если индикатор в точке `i` использует данные баров `> i`,
стратегия «знает будущее» и заведомо прибыльна на истории. Это нужно поймать
**до** любой оптимизации.

**Модель исполнения проекта уже защищает на уровне движка:** сигнал считается
по закрытию бара `i`, а исполняется по **открытию `i+1`** (плюс
проскальзывание/спред). Вы физически не можете купить по цене, которую увидели
только после закрытия свечи.

**Но логика индикаторов — на вашей совести:**
- Безопасно (смотрит в прошлое): `rolling`, `ewm`, `shift(+k)`.
- Опасно (тихо подмешивает будущее): `shift(-k)`, `center=True`, `bfill`,
  нормировка по всему ряду `(x - x.mean())/x.std()`, `close[i+1]`.

**Что сделать.**
- Для событийного движка (`BaseStrategy`) — отдельный тест в `tests/` ловит
  lookahead автоматически (срезы данных до бара `i`).
- Для быстрого движка (`SignalStrategy`) защита срезами **не работает** —
  `compute_signals()` видит весь массив сразу. Поэтому **обязательно**:
  ```python
  from backtester.fast_engine import assert_no_lookahead
  assert_no_lookahead(MySignal, df, {"period": 20})  # пересчёт на префиксах
  ```
- Прогоните весь набор тестов фреймворка:
  ```bash
  pytest
  ```
  Помимо анти-lookahead он проверяет **побитовую эквивалентность** двух движков
  (быстрый numba ≡ событийный) — гарантия, что ускорение не меняет модель.

> ⚠️ Если стратегия не проходит этот шаг — дальше идти нельзя. Любые красивые
> метрики будут фикцией.

## Шаг 3. Одиночный бэктест с реалистичными издержками

**Зачем.** Базовая оценка стратегии на дефолтных (осмысленных) параметрах,
*как есть*, без оптимизации. Цель — не «красивая цифра», а проверка механики и
жизнеспособности идеи с учётом реальных издержек. Издержки убивают
высокочастотные стратегии — их нужно закладывать с первого прогона.

**Что сделать.**
- Задайте **реалистичные** издержки (не нули!): комиссию за сторону,
  проскальзывание, спред (данные = bid, покупка по ask), при необходимости —
  плечо `max_leverage`:
  ```python
  ENGINE_KWARGS = dict(cash=10_000.0, commission_pct=0.0005, slippage_pct=0.0001)
  ```
  В GUI — поля слева. Запустите бэктест (`python main.py` или кнопка «Старт»).
- **Стресс-тест издержками** (Опыт 2 из GUIDE): прогоните с `commission_pct=0`
  и с завышенной (например 0.2%). Если небольшой рост издержек убивает прибыль
  — стратегия неробастна, преимущество тоньше спреда.
- Посмотрите сделки и маркеры на графике: совпадает ли поведение с замыслом?
  Нет ли аномалий (одна сделка дала 90% прибыли — это не стратегия, а везение)?

**На что смотреть.** Экспозиция (`exposure_pct` — сколько времени в рынке),
число сделок (мало сделок = недостоверная статистика), доля выходов по
SL/TP/сигналу.

## Шаг 4. Интерпретация метрик

**Зачем.** Net Profit — худшая метрика для оценки: она игнорирует риск и путь.
Профессионал смотрит на риск-скорректированную доходность и устойчивость.

**Ключевые метрики проекта (класс `PerformanceMetrics`)** и как их читать:

| Метрика | Что показывает | Ориентир |
|---|---|---|
| `sharpe_ratio` | доходность на единицу волатильности | > 1 неплохо, > 2 отлично (но см. шаг 6 — Sharpe легко раздуть перебором) |
| `sortino_ratio` | как Sharpe, но штрафует только падения | выше Sharpe — асимметрия в нашу пользу |
| `calmar_ratio` | CAGR% / MaxDD% | > 1 — доходность покрывает худшую просадку за год |
| `max_drawdown_pct` | худшее падение от пика | переживёте ли психологически и по капиталу? |
| `max_drawdown_duration` | как долго сидели в просадке (баров) | длинная просадка = отказ от стратегии раньше восстановления |
| `recovery_factor` | net_profit / max_drawdown | способность отбивать просадки |
| `profit_factor` | сумма прибылей / сумма убытков | > 1.5 здорово; ~1.0 — на грани |
| `win_rate_pct` | % прибыльных сделок | сам по себе бесполезен без размера сделок |
| `expectancy` | матожидание на сделку | должно быть > 0 и > издержек |
| `max_consecutive_losses` | серия убытков подряд | планирование риска и психологии |
| `complex_criterion` | комплексный критерий (как в MT5) | сводная оценка для оптимизации |

**Правило.** Не выбирайте стратегию по одной метрике. Высокий Sharpe с
просадкой 60% и серией из 15 убытков — нерабочая в реале система. Смотрите
связку: риск-скорр. доходность + просадка + устойчивость.

## Шаг 5. Оптимизация (in-sample)

**Зачем.** Найти область хороших параметров — но с ясным пониманием, что
**оптимизация подгоняет под историю**. Результат оптимизации сам по себе
торговать нельзя; это лишь сырьё для проверок на шагах 6–9.

**Что сделать.**
- Выберите критерий оптимизации осознанно: оптимизация под Net Profit даёт
  переторгованные хрупкие пики; под `sharpe_ratio` / `calmar_ratio` /
  `complex_criterion` — более устойчивые. (CLI: `make_backtest_objective(metric=...)`;
  GUI — выпадающий список «Критерий».)
- Метод:
  - **Grid Search** — полный перебор, видит весь ландшафт (нужен для шага 5).
  - **Genetic** — когда комбинаций слишком много для полного перебора.
- **Ограничьте сетку разумным числом значений.** Чем больше комбинаций
  (`n_trials`), тем сильнее раздувается лучший Sharpe чисто статистически — и
  тем строже будет дефляция на шаге 6. В GUI под таблицей параметров — живой
  счётчик комбинаций (красным, если слишком много).
- Ускорьте перебор: поле «Процессы CPU» (авто = все ядра минус один). Для
  массовой оптимизации используйте `SignalStrategy` + быстрый numba-движок
  (десятки раз быстрее, результат побитово тот же).

```python
objective = make_backtest_objective(df, MyStrategy, metric="sharpe_ratio",
                                     engine_kwargs=ENGINE_KWARGS)
grid = GridSearchOptimizer(objective, param_grid={
    "fast_period": range(5, 30, 5), "slow_period": range(30, 110, 20)})
result = grid.optimize()
```

> ⚠️ Запомните `len(result.history)` (= `n_trials`): это вход для дефляции
> Sharpe на шаге 6. Чем больше перебрали — тем меньше веры лучшему результату.

## Шаг 6. Защита от data snooping

Это первый по-настоящему жёсткий фильтр. Лучший результат перебора почти
всегда завышен: **максимум из N случайных величин растёт с N**, даже если
преимущества нет. Здесь мы это количественно проверяем — четырьмя
независимыми инструментами.

### 6а. Ландшафт оптимизации — плато против пика

**Зачем.** Робастный оптимум — это **широкое плато**: соседние комбинации
параметров дают похоже хорошие результаты. Одинокий яркий пик среди провалов
= переподгонка: малейший сдвиг рынка — и вы на склоне.

**Что сделать (GUI, вкладка «Опт. графики»).**
- **Тепловая карта** по двум параметрам: ищите широкое ровное светлое пятно
  (плато), а не одиночную яркую ячейку.
- **Гистограмма score**: если лучший результат (зелёный пунктир) висит в пустом
  правом хвосте, оторванный от массы — это аномалия/везение, признак подгонки.

**Выбор параметров по плато** вместо argmax:
```python
from backtester import select_plateau_params
params, _ = select_plateau_params(result.history)  # лучшее среднее по окрестности
```

### 6б. Deflated Sharpe Ratio (DSR)

**Зачем.** DSR отвечает: значим ли лучший Sharpe **с поправкой на число
испытаний** и на асимметрию/эксцесс доходностей (Bailey & López de Prado).

**Что сделать.** Считается автоматически и печатается в отчётах оптимизации
(CLI и GUI) и WFA. Вручную:
```python
from backtester import deflated_sharpe_from_optimization
dsr = deflated_sharpe_from_optimization(df, MyStrategy, result.best_params,
                                        n_trials=len(result.history),
                                        engine_kwargs=ENGINE_KWARGS)
```
**Порог: `DSR > 0.95`** — результат значим даже с учётом перебора. Меньше —
лучший Sharpe объясним просто множественным тестированием.

Сопутствующие инструменты модуля `statistics`: `min_track_record_length`
(MinTRL — хватает ли длины истории, чтобы Sharpe был достоверным),
`haircut_sharpe_ratio` (на сколько «срезать» Sharpe с поправкой на снупинг),
`effective_number_of_trials`, `expected_max_sharpe`.

### 6в. Permutation-тест

**Зачем.** Эксплуатирует ли стратегия именно **временнУю структуру** рынка, а
не свойства распределения? История многократно перемешивается (геометрия баров
и распределение доходностей сохраняются, порядок разрушается).

```python
from backtester import permutation_test
print(permutation_test(df, MyStrategy, best_params))  # p-value против шума
```
**Порог:** малое `p-value` (≤ 0.05) — преимущество в порядке баров реально, а
не в форме распределения.

### 6г. PBO / CSCV — вероятность переподгонки

**Зачем.** Самый важный вопрос отбора, на который DSR **не** отвечает:
*«систематически ли конфигурация, лучшая на in-sample, проваливается на
out-of-sample?»*. Метод CSCV (Combinatorially Symmetric Cross-Validation)
режет историю на блоки, перебирает все способы поделить их на IS/OOS, и
смотрит, переносится ли «лучший по IS» на OOS.

```python
from backtester import pbo_from_optimization
pbo = pbo_from_optimization(df, MyStrategy, result.history, engine_kwargs=ENGINE_KWARGS)
print(pbo)
```
**Порог: PBO близка к 0** — преимущество переносится на новые данные.
**PBO ≈ 0.5** — отбор лучшего по IS равносилен подбрасыванию монеты на OOS:
чистая переподгонка. Побочно метод даёт деградацию OOS↔IS и вероятность убытка
отобранной конфигурации на OOS.

> Шаги 6б–6г используют **одни и те же** `result` и `n_trials` с шага 5. Если
> стратегия валится здесь — возвращайтесь к гипотезе (шаг 0), а не «крутите
> параметры дальше»: это и есть data mining.

## Шаг 7. Walk-Forward Analysis (WFA)

**Зачем.** Главная проверка на устойчивость: работают ли параметры на данных,
которые оптимизатор **не видел**? История режется на окна; в каждом окне
параметры оптимизируются на in-sample (IS) и прогоняются на следующем,
невиданном out-of-sample (OOS). OOS-прогоны сшиваются в одну кривую с
компаундингом — **честная симуляция реальной торговли с периодической
переоптимизацией**.

**Что сделать (GUI: настройки «Walk-Forward», кнопка, вкладка «Дашборд»).**
- Задайте длину IS, длину OOS, смещение (0 = смещение равно OOS — классика без
  зазоров). Режим: rolling (окно скользит) или anchored (начало IS закреплено,
  окно растёт).
- **`warmup_bars`**: подаёт хвост IS в каждый OOS-прогон для прогрева
  индикаторов (торговля на нём запрещена). Без него первые бары окна стратегия
  «слепа». Обязательно для индикаторов с длинным периодом.
- **Purge** (встроен): разрыв между IS и OOS, чтобы перекрывающиеся по времени
  сделки не «протекали» из обучения в проверку — защита от утечки на стыке окон.

**Главная метрика — Walk-Forward Efficiency (WFE):** отношение скорости
заработка на OOS к скорости на IS (доходность на бар), в %:
- **WFE ≈ 100%** — на новых данных как на истории (идеал);
- **WFE 50–70%** — умеренная деградация, обычно приемлемо;
- **WFE ≤ 0** — оптимизация ловит шум, **торговать нельзя**.

**Дополнительно смотрите:**
- **Доля прибыльных окон** ≥ 60% (консистентность, а не один удачный кусок).
- **Разброс OOS-доходностей** — стабильны ли результаты от окна к окну.
- **Стабильность параметров** (CV): если лучшие параметры скачут от окна к
  окну — оптимум нестабилен, у стратегии нет устойчивого «настоящего» значения.
- На дашборде: эволюция параметров, WFE каждого окна, IS vs OOS доходность.

## Шаг 8. Матричный WFO (поиск плато по длинам окон)

**Зачем.** Тонкая, но критичная мысль: **сами длины окон IS/OOS — это тоже
параметры**, которые можно неосознанно подогнать. Удачный WFE при IS=180/OOS=45
ничего не значит, если при IS=160/OOS=40 всё рушится. Матричный WFO прогоняет
полный walk-forward для каждой комбинации длин из двух диапазонов (IS × OOS) и
ищет **плато устойчивости**.

**Что сделать (GUI: кнопка «Матричный WFO», вкладка «Матрица WFO»).**
```python
from backtester import WfaMatrixConfig, run_wfa_matrix
cfg = WfaMatrixConfig.from_ranges(df.index[0], df.index[-1],
        is_range=(90, 360, 4), oos_range=(20, 90, 4))   # (min, max, count)
res = run_wfa_matrix(df, MyStrategy, cfg, grid={"fast": [5, 10, 15]},
                     metric="sharpe_ratio", target="wfe_pct", n_jobs=0)
print(res)                  # сводка + рекомендованные длины IS/OOS
print(res.matrix("wfe_pct"))   # тепловая карта (IS × OOS)
robust = res.robust_cell()  # центр лучшего плато
```
**Как читать тепловую карту:**
- **Широкая область соседних хороших ячеек (плато)** — стратегия устойчива к
  выбору длин окон. Это сильный сигнал робастности.
- **Одинокий яркий пик среди провалов** — переподгонка под конкретную нарезку.

**Сводные числа:** средняя WFE по сетке, доля прибыльных ячеек, коэффициент
вариации целевой метрики (чувствительность к длинам окон), и **рекомендация —
центр лучшего плато** (максимум среднего по окрестности 3×3, а не глобальный
пик). Двойной клик по ячейке подставляет её длины IS/OOS в настройки WFA.

## Шаг 9. Монте-Карло (риск и план капитала)

**Зачем.** Бэктест даёт **одну** кривую эквити — одну случайную реализацию
порядка сделок. Вам повезло или нет — неизвестно. Монте-Карло строит из тех же
сделок тысячи альтернативных кривых и отвечает на главный вопрос управления
капиталом: *«каков разброс возможных исходов и какой риск разорения?»*.

**Что сделать (GUI: кнопка «Монте-Карло», вкладка с дашбордом).**
- **Метод:**
  - *перестановка* — те же сделки в новом порядке (итог фиксирован; оцениваем
    разброс просадок и серий убытков);
  - *бутстрэп* — сделки тянутся с возвратом (меняется и итог, и путь);
  - *блочный бутстрэп* — блоки подряд идущих сделок (сохраняет кластеры
    удачных/неудачных периодов — ближе к реальной автокорреляции).
- **Сайзинг:** реинвестирование (компаундинг) или фиксированный размер.
- Задайте **цель / лимит просадки / порог разорения** для расчёта вероятностей.

**Что вы получаете и как использовать:**
- Интервалы доходности (P5…P95), **VaR/CVaR 95%**, просадка P50/P95/худшая.
- **Вероятность разорения** и превышения лимита просадки — go/no-go по риску.
- **План капитала по P95 просадки, а не по бэктесту.** Просадка в одном
  бэктесте почти всегда оптимистична; закладывайте капитал на P95.

**Блок защиты от переоптимизации (внизу сводки):**
- **Сценариев с убытком (p-value)** ≤ 5% — преимущество устойчиво; > 25% —
  прибыли могло и не быть (хрупко).
- **Перцентиль бэктеста** ≥ 95% — исходная кривая аномально удачна среди своих
  же перестановок: красота графика = везение порядка сделок.
- **Симуляций с DD ≤ исходной** ≤ 5% — просадка в бэктесте нетипично мала, в
  реале будет глубже.
- **90% ДИ матожидания на сделку** — если интервал накрывает ноль,
  положительное матожидание **не доказано**.

## Шаг 10. Решение go / no-go — финальный чек-лист

Стратегию можно рассматривать для торговли (на демо/малом объёме), только если
пройдены **все** ворота. Один проваленный пункт — стоп и возврат к гипотезе.

- [ ] **Гипотеза** имеет экономический смысл (шаг 0).
- [ ] **Данные** чистые, покрывают разные режимы; **`sanity_check` = всё OK** (шаг 1).
- [ ] **`pytest` зелёный**, `assert_no_lookahead` пройден — нет заглядывания в
      будущее (шаг 2).
- [ ] Стратегия **прибыльна с реалистичными издержками** и не разваливается при
      их росте (шаг 3).
- [ ] Риск-метрики приемлемы: просадка переживаемая, Sharpe/Calmar, серии
      убытков (шаг 4).
- [ ] Оптимум — **плато**, не одинокий пик; лучший результат не в пустом хвосте
      гистограммы (шаги 5–6а).
- [ ] **DSR > 0.95**; MinTRL достаточен; **permutation p ≤ 0.05**; **PBO мала
      (≪ 0.5)** (шаг 6).
- [ ] **WFE ≥ 50%**, доля прибыльных окон ≥ 60%, параметры стабильны между
      окнами (шаг 7).
- [ ] **Матричный WFO**: есть плато по длинам окон, не одиночный пик (шаг 8).
- [ ] **Монте-Карло**: риск разорения приемлем, ДИ матожидания не накрывает
      ноль, капитал спланирован по P95 просадки (шаг 9).

**Даже после всех ворот:** запускайте на **бумаге / малом объёме (paper /
forward-тест на живых данных)** прежде чем рисковать капиталом. Бэктест — это
прошлое; единственная честная проверка — будущее, которого не видел никто, в
том числе вы.
