Это пошаговая инструкция: как разобраться в проекте, как его запускать
и как проверить, что всё работает правильно.

## Шаг 1. Общая картина: как части связаны между собой

Представьте конвейер из 5 станков:

```
 CSV-файл с историей цен
        │
        ▼
 [data_loader]  ──  читает файл, чистит мусор, проверяет данные
        │
        ▼
 [backtest_engine] ── «проигрывает» историю бар за баром и передаёт
        │              каждый бар вашей стратегии; исполняет её приказы
        │              (купить/продать), считает комиссии, SL/TP
        ▼
 [metrics]      ──  по итогам считает оценки: прибыль, просадку, Шарпа...
        │
        ▼
 [optimizer]    ──  запускает бэктест много раз с разными параметрами
        │              и ищет лучшие
        ▼
 [monte_carlo]  ──  перемешивает сделки бэктеста тысячи раз и строит
        │              распределение доходностей/просадок вместо одной кривой
        ▼
 [walk_forward] ──  гоняет «оптимизация → проверка на новых данных»
        │              по скользящим окнам и оценивает устойчивость
        ▼
 [visualizer]   ──  рисует интерактивные графики в HTML-файлы
```

Ваша стратегия (папка `strategies/`) — это «картридж», который вставляется
в движок. Движок не знает, что внутри стратегии, стратегия не знает, как
устроен движок. Они общаются через два метода:

- `init()` — вызывается **один раз** перед стартом. Здесь вы заранее
  считаете индикаторы (как буфера индикатора в MQL5).
- `next(bar)` — вызывается **на каждой свече** по очереди, от старых к новым.
  Это аналог `OnTick()`/`OnCalculate()` в MT5, только раз в бар.

Движков два, с **одинаковой моделью исполнения**:

- **Событийный** (`backtest_engine`) — гибкий, бар за баром, для любой
  логики (трейлинг, лимитные/стоп-ордера, состояние между барами). Базовый
  класс — `BaseStrategy` (`init` + `next`).
- **Быстрый** (`fast_engine`, на numba) — для «сигнальных» стратегий: одна
  неттинг-позиция и защитные SL/TP по заранее посчитанным сигналам. Базовый
  класс — `SignalStrategy`. На 100k баров он быстрее событийного в десятки
  раз — это то, что делает массовую оптимизацию и Walk-Forward комфортными
  на слабом CPU. Результат **побитово совпадает** с событийным движком.

Начните с событийного (его проще понять), а на оптимизацию/WFA переводите
стратегию в сигнальную форму. Подробности — в Шаге 4а.

Внутри `next()` вам доступно:

| Что написать          | Что это значит                                  |
|-----------------------|--------------------------------------------------|
| `bar.close`, `bar.high` | цены текущего бара                             |
| `self.close`          | массив всех цен закрытия ДО текущего бара включительно |
| `self.position`       | открытая позиция или `None`, если её нет        |
| `self.buy(...)` / `self.sell(...)` | купить / продать (можно с SL и TP) |
| `self.close_position()` | закрыть позицию                                |
| `self.equity`         | текущая стоимость счёта                         |

## Шаг 2. В каком порядке читать файлы

Читайте сверху вниз, в каждом файле в начале есть описание на русском:

1. `strategies/sma_cross.py` — **начните отсюда**. Это пример стратегии для
   событийного движка, всего ~60 строк. Поняв его, вы поймёте 80% того, как
   пользоваться фреймворком.
1б. `strategies/sma_cross_signal.py` — та же стратегия в «сигнальной» форме
   для быстрого numba-движка (`backtester/fast_engine.py`). Сравните оба
   файла — увидите, как одна логика выражается двумя способами.
2. `main.py` — как собрать всё вместе: загрузить данные, запустить тест,
   оптимизацию, сохранить графики.
3. `backtester/base_strategy.py` — какие ещё «кнопки» есть у стратегии.
4. `backtester/metrics.py` — какие метрики считаются (просто список полей
   в классе `PerformanceMetrics` с комментариями).
5. `backtester/backtest_engine.py` — ядро. Самый сложный файл, читать
   целиком необязательно. Главное — прочитать комментарий в шапке файла:
   там описаны правила исполнения ордеров.
6. `backtester/data_loader.py` и `backtester/optimizer.py` — по мере надобности.

## Шаг 3. Запуск через GUI (самый простой способ)

Откройте терминал в папке проекта (в VS Code: меню Terminal → New Terminal)
и выполните:

```
python desktop_app.py
```

Откроется десктопный «Тестер стратегий» — окно в стиле тестера MT5:

1. **Слева**: данные (кнопка «Открыть CSV...» для экспорта из MT5 или
   синтетика), период теста, капитал и издержки, стратегия, критерий
   и метод оптимизации.
2. **Вкладка «Параметры» внизу**: значения для бэктеста; для оптимизации
   поставьте галочку «Опт.» и задайте Старт/Шаг/Стоп. Под таблицей —
   живой счётчик: сколько значений даёт каждый параметр и сколько всего
   комбинаций получится (для полного перебора; красным — если их слишком
   много). В режиме генетики дополнительно показано число прогонов
   (популяция × поколения).
3. Кнопка **«Старт (бэктест)»** — метрики во вкладке «Результаты», сделки
   во вкладке «Сделки», на графике появятся маркеры входов/выходов и эквити.
4. Кнопка **«Оптимизация»** — прогресс в статус-баре; результаты во вкладке
   «Оптимизация» (сортировка по клику на заголовок). По завершении лучшие
   параметры автоматически прогоняются бэктестом. Двойной клик по любой
   строке — прогнать её параметры. Поле **«Процессы CPU»** распараллеливает
   оптимизацию (и WFA) по ядрам: «авто» = все ядра минус одно,
   1 = выключить. Результаты побитово совпадают с однопоточными.
5. **Вкладка «Опт. графики»**: тепловая карта ландшафта оптимизации по двум
   выбранным параметрам (широкое ровное светлое пятно — плато, одиночная
   яркая ячейка — нестабильный пик) и гистограмма распределения score
   (зелёный пунктир — лучший результат; если он висит в пустом хвосте —
   признак переподгонки). Свёртка остальных параметров — среднее или
   максимум; наведение мыши на ячейку показывает её параметры и score.
6. График: колесо мыши — зум, перетаскивание — прокрутка. Держит сотни
   тысяч свечей без лагов. Граница между ценой и эквити перетаскивается
   мышью — панель эквити можно увеличить или свернуть совсем.

После правок в папке gui/ запускайте `python gui_smoke_test.py` — быстрая
проверка, что интерфейс не сломан.

## Шаг 3б. Walk-Forward Analysis (проверка на устойчивость)

Оптимизация подгоняет параметры под историю. WFA проверяет, работают ли
они на данных, которые оптимизатор **не видел**: история режется на окна,
в каждом окне параметры оптимизируются на in-sample участке (IS), а затем
прогоняются на следующем за ним out-of-sample участке (OOS). Все
OOS-прогоны сшиваются в одну кривую с компаундингом — это симуляция
реальной торговли с периодической переоптимизацией.

Как запустить в GUI:

1. Во вкладке «Параметры» отметьте «Опт.» и задайте Старт/Шаг/Стоп —
   сетка та же, что у обычной оптимизации; критерий и метод (Grid/генетика)
   берутся из блока «Стратегия и оптимизация».
2. В блоке **«Walk-Forward (WFA)»** задайте длину окна IS, окна OOS и
   смещение (0 = смещение равно OOS — классика без зазоров; меньше OOS
   нельзя — участки перекрылись бы). Галочка «Якорное IS» — начало IS
   закреплено на старте периода, окно растёт. Под настройками — живой
   счётчик: сколько окон и прогонов получится из выбранных дат.
3. Кнопка **«Walk-Forward»** — прогресс и текущее окно в статус-баре.
4. Вкладка **«Walk-Forward» → «Дашборд»**: слева сводка устойчивости,
   справа графики — сшитая OOS-эквити с подсветкой окон, таймлайн окон
   IS→OOS, доходность IS vs OOS по окнам (в % годовых), эволюция лучших
   параметров от окна к окну, WFE каждого окна.
5. Вкладка **«Окна»**: таблица всех окон с датами, параметрами и
   результатами; двойной клик — подставить параметры окна в таблицу
   «Параметры» и прогнать бэктест.

Главная метрика — **Walk-Forward Efficiency (WFE)**: отношение скорости
заработка на OOS к скорости заработка на IS (доходность на бар), в %:

- **WFE ≈ 100%** — на новых данных стратегия работает как на истории;
- **WFE 50–70%** — умеренная деградация, обычно приемлемо;
- **WFE ≤ 0** — оптимизация ловит шум, торговать такие параметры нельзя.

Дополнительно смотрите: долю прибыльных окон (хорошо ≥ 60%), разброс
OOS-доходностей и стабильность параметров (CV — если лучшие параметры
скачут от окна к окну, оптимум нестабилен).

## Шаг 3в. Монте-Карло (анализ вероятностей)

Бэктест даёт **одну** кривую эквити — одну случайную реализацию порядка
сделок. Монте-Карло строит из тех же сделок тысячи альтернативных кривых
и отвечает: каков **разброс** возможных исходов, а не «что было однажды».

Как запустить в GUI:

1. Прогоните обычный бэктест (кнопка «Старт»).
2. Кнопка **«Монте-Карло»** слева (или «Запустить» во вкладке
   «Монте-Карло») — настройки в самой вкладке:
   - **Метод**: *бутстрэп* (сделки тянутся с возвратом — меняется и итог,
     и путь), *перестановка* (те же сделки в новом порядке — итог
     фиксирован, оценивается разброс просадок и серий убытков),
     *блочный бутстрэп* (блоки подряд идущих сделок — сохраняет кластеры
     удачных/неудачных периодов);
   - **Сайзинг**: реинвестирование (% от счёта, компаундинг) или
     фиксированный размер ($);
   - **Сделок на путь**: длина каждого сценария будущего (0 = как в
     бэктесте; больше — заглянуть на несколько «бэктестов» вперёд);
   - **Цель / лимит просадки / порог разорения** — для расчёта вероятностей.
3. Слева — сводка: интервалы доходности (P5…P95), VaR/CVaR 95%,
   просадка P50/P95/худшая, вероятности (прибыль, достижение цели,
   превышение лимита DD, риск разорения), серии убытков.
4. Справа — графики: веер кривых эквити с перцентильными конвертами
   и белой кривой исходного бэктеста, гистограммы доходностей / просадок /
   серий убытков, CDF доходности.

Защита от переоптимизации (блок внизу сводки):

- **Сценариев с убытком (p-value)** — доля перемешиваний, закончившихся
  в минусе. ≤ 5% — преимущество статистически устойчиво; > 25% — результат
  хрупок, прибыли могло и не быть.
- **Перцентиль бэктеста** ≥ 95% — исходная кривая аномально удачна среди
  своих же перестановок: красота графика — везение порядка сделок.
- **Симуляций с DD ≤ исходной** ≤ 5% — просадка в бэктесте нетипично
  мала, в реальной торговле почти наверняка будет глубже (планируйте
  капитал по P95 просадки, а не по бэктесту).
- **90% ДИ матожидания на сделку** — если интервал накрывает ноль,
  положительное матожидание не доказано.

## Шаг 4а. Как добавить свою стратегию в проект

Стратегия — это всегда **класс-наследник `BaseStrategy`**, который лежит
в папке `strategies/` и **зарегистрирован** в `strategies/__init__.py`.
Просто положить файл в папку недостаточно — движок и GUI узнают о стратегии
только через реестр `STRATEGIES`. Три действия:

**1. Создайте файл** `strategies/my_strategy.py`. Проще всего скопировать
`sma_cross.py` и переписать условия. Минимальный каркас:

```python
from backtester import BaseStrategy, Bar
import numpy as np
import pandas as pd

class MyStrategy(BaseStrategy):
    params = {"period": 20, "sl_pct": 0.02, "tp_pct": 0.05}

    def init(self) -> None:
        # считается ОДИН раз; full_close — все цены закрытия целиком
        self.sma = pd.Series(self.full_close).rolling(int(self.p["period"])).mean().to_numpy()

    def next(self, bar: Bar) -> None:
        i = bar.index
        if np.isnan(self.sma[i]):
            return                       # индикатор ещё не прогрелся — пропускаем бар
        if bar.close > self.sma[i] and not self.position:
            self.buy(stop_loss=bar.close * (1 - self.p["sl_pct"]),
                     take_profit=bar.close * (1 + self.p["tp_pct"]))
        elif bar.close < self.sma[i] and self.position:
            self.close_position()
```

**2. Зарегистрируйте её** в `strategies/__init__.py` — добавьте импорт
и строку в словарь `STRATEGIES`:

```python
from .my_strategy import MyStrategy          # импорт нового класса

STRATEGIES = {
    "SMA Crossover (пересечение скользящих)": SmaCrossStrategy,
    "Моя стратегия (SMA + SL/TP)": MyStrategy,   # ключ = имя в списке GUI
}
```

**3. Запустите** `python desktop_app.py` — стратегия появится в выпадающем
списке слева, а её `params` сами превратятся в строки таблицы «Параметры»
(с галочками «Опт.» для оптимизации).

### Если что-то пошло не так

| Ошибка при запуске | Причина | Что сделать |
|--------------------|---------|-------------|
| `ModuleNotFoundError: No module named 'strategies.xxx'` | в `__init__.py` импорт из несуществующего/переименованного файла | поправьте имя файла в `from .xxx import ...` |
| `ImportError: cannot import name 'MyStrategy'` | файл есть, но в нём нет такого класса (например, там только функция-индикатор) | оберните логику в класс-наследник `BaseStrategy` |
| Стратегии нет в списке GUI | класс не добавлен в словарь `STRATEGIES` | добавьте строку в `STRATEGIES` |

### Важные правила (иначе результат будет нечестным или медленным)

- **Тяжёлые вычисления — в `init()`**, а не в `next()`: `init()` зовётся
  один раз, `next()` — на каждом баре.
- **Индикаторы считайте векторно** (`rolling`/`ewm`/операции numpy на всём
  массиве), без Python-цикла по барам. При оптимизации `init()` выполняется
  на каждой комбинации параметров — цикл в нём сведёт на нет всю выгоду
  быстрого движка.
- **Без заглядывания в будущее**: индикатор в точке `i` должен зависеть
  только от баров ≤ `i`. `rolling`/`ewm`/`shift(+k)` смотрят в прошлое — это
  безопасно. Опасно и тихо ломает причинность: `shift(-k)`, `center=True`,
  `bfill`, нормировка по всему ряду (`(x-x.mean())/x.std()`). Брать
  `close[i+1]` нельзя. Отдельный тест в `tests/` это ловит.
- **Сигнал → исполнение на следующем баре**: рыночный ордер с бара `i`
  исполнится по открытию `i+1` (см. «Частые вопросы»). Это не баг.

### Быстрая версия для оптимизации/WFA (SignalStrategy)

Когда стратегия — это «по сигналу встать в лонг/шорт с SL/TP», её стоит
написать как `SignalStrategy` для быстрого numba-движка: оптимизация и
Walk-Forward ускоряются в десятки раз. Логика выражается **массивами**:
в `compute_signals()` заполняете `self._sig[i]` (+1/−1/0), `self._sl[i]`,
`self._tp[i]` (абсолютные уровни, `NaN` — нет), при желании `self._size[i]`
или `self._risk[i]`. Тот же класс работает и на событийном движке.

```python
import numpy as np, pandas as pd
from backtester.fast_engine import SignalStrategy, run_fast_backtest, assert_no_lookahead

class MySignal(SignalStrategy):
    params = {"period": 20, "sl_pct": 0.02, "tp_pct": 0.05}

    def compute_signals(self) -> None:
        prices = self.full_close
        sma = pd.Series(prices).rolling(int(self.p["period"])).mean().to_numpy()
        # ВЕКТОРНО (без цикла): пробой SMA снизу вверх -> сигнал в лонг
        up = (prices[:-1] <= sma[:-1]) & (prices[1:] > sma[1:])
        idx = np.flatnonzero(up & ~np.isnan(sma[:-1])) + 1
        self._sig[idx] = 1
        self._sl[idx] = prices[idx] * (1 - self.p["sl_pct"])
        self._tp[idx] = prices[idx] * (1 + self.p["tp_pct"])

result = run_fast_backtest(df, MySignal, {"period": 20}, commission_pct=0.0005)
assert_no_lookahead(MySignal, df, {"period": 20})   # обязательная проверка причинности
```

**Почему обязателен `assert_no_lookahead`.** В сигнальной форме нет
страховки «срезов до бара `i`» — `compute_signals()` видит весь массив
сразу. Прогон на событийном движке тоже не докажет причинность (оба движка
читают одни и те же предрассчитанные сигналы). `assert_no_lookahead`
пересчитывает сигналы на префиксах данных и ловит зависимость от будущего —
вызывайте её для каждой новой сигнальной стратегии. Образец — готовый файл
`strategies/sma_cross_signal.py`.

### Особый случай: у меня уже есть готовый индикатор-функция

Часто индикатор уже написан отдельной функцией `signals(df, ...)` (перенос
из TradingView/MT5). Сама по себе функция стратегией не является — тестеру
нужен **класс**. Оберните её: в `init()` (или `compute_signals()` для
быстрого движка) один раз вызовите функцию и сохраните массивы сигналов, а
торгуйте по ним через `bar.index`. Если внутри функции есть итеративный
расчёт (состояние зависит от предыдущего бара) — вынесите этот цикл в
отдельную `@njit`-функцию, иначе он станет узким местом при оптимизации.

## Шаг 5. Эксперименты (лучший способ разобраться)

Меняйте по одной вещи и смотрите, как меняется результат.

**Опыт 1 — параметры стратегии.** В `main.py` найдите строку
`strategy_params={"fast_period": 10, "slow_period": 30}` и поставьте другие
числа. Запустите. Метрики и график изменились?

**Опыт 2 — комиссия.** В `main.py` в `ENGINE_KWARGS` поставьте
`commission_pct=0.0` и запустите, потом `0.002` (0.2%) и сравните
`net_profit` и `total_commission`. Прибыль должна заметно падать с ростом
комиссии — так вы убедитесь, что издержки реально учитываются.

**Опыт 3 — стоп-лосс.** В `strategies/sma_cross.py` поставьте очень близкий
стоп `"sl_pct": 0.001` (0.1%). В отчёте почти все выходы должны стать
`stop_loss`, а сделки — короткими.

**Опыт 4 — своя мини-стратегия.** Скопируйте `sma_cross.py` в новый файл,
поменяйте условия входа (например, «закрытие выше максимума за 20 баров»)
и зарегистрируйте в `strategies/__init__.py` — подробно это разобрано
в **Шаге 4а**. После этого она появится в списке GUI.

## Шаг 6. Как убедиться, что движок считает честно (чек-лист)

Эти проверки уже оформлены готовым скриптом — запустите:

```
python sanity_check.py
```

Что он проверяет и почему это важно:

1. **Сходимость баланса.** Сумма прибылей всех сделок должна совпадать
   с изменением счёта (финальный капитал − стартовый). Если бы движок
   «терял» или «рисовал» деньги — это бы вскрылось здесь.
2. **Стратегия «не торгую» = ноль сделок и ровная эквити.** Пустая
   стратегия не должна ничего заработать или потерять.
3. **Без комиссий и проскальзывания прибыль выше**, чем с ними, на тех же
   данных и параметрах.
4. **SL и TP срабатывают по своим ценам.** Для сделок с выходом
   `stop_loss` цена выхода не лучше уровня стопа (с поправкой на гэп
   и проскальзывание).
5. **Воспроизводимость.** Два запуска на одних данных дают одинаковый
   результат до копейки.

Если все пять пунктов печатают `OK` — ядру можно доверять и строить дальше.

## Шаг 7. Автономная торговля на сервере (VPS) без графики

Окно «Торговля» удобно, когда вы сидите за компьютером. Но чтобы стратегия
работала **круглосуточно**, её запускают на VPS (арендованном сервере) — там нет
экрана, поэтому GUI не годится. Для этого есть **консольный раннер `algo-live`**:
тот же торговый движок, но управляется текстовым файлом-настройкой и пишет
происходящее в журнал.

> ⚠️ Это уже **реальные ордера**. Сначала прогоните стратегию на демо/тестнете и в
> режиме «сухого прогона», и только потом — на реале малым размером. Раннер
> намеренно не даст случайно запустить реал (см. ниже про `--yes`).

**1. Установите зависимости торговли и создайте файл-настройку.**

```
pip install -e ".[live]"
cp live/trade.example.json ~/trade.json
```

Откройте `~/trade.json` в любом редакторе. Это обычный текст; главные поля:

- `exchange` — `"lighter"` или `"bingx"`; `mode` — `"demo"` (тестнет) или `"real"`;
- `symbol`, `timeframe` — что и на каком таймфрейме торговать;
- `strategy` — **точное имя** стратегии (как в выпадающем списке GUI) или имя её
  класса; `strategy_params` — её параметры (те же, что вы подбирали в тестере);
- `sizing` — размер позиции; `risk` — предохранители (дневной лимит убытка и т.п.);
- `execution.require_protective` — оставьте `true`: если биржа **не примет
  стоп-лосс**, раннер сам закроет позицию и остановится, а не оставит её без защиты
  (особенно важно на DEX Lighter).

**2. Дайте раннеру ключи.** В файл-настройку их **не пишут** (это секреты). Либо
один раз введите их в GUI (окно «Торговля» → «Проверить подключение») — раннер
возьмёт их из того же хранилища; либо задайте переменными окружения (в верхнем
регистре с префиксом `ALGO_CRED_`):

```
export ALGO_CRED_PRIVATE_KEY=...        # Lighter: приватный ключ API
export ALGO_CRED_ACCOUNT_INDEX=0
export ALGO_CRED_API_KEY_INDEX=4
# для BingX вместо этого: ALGO_CRED_API_KEY и ALGO_CRED_SECRET
```

**3. Прогон вживую.** Сначала безопасно — «сухой прогон» (цикл работает, но ордера
не отправляются), потом реал:

```
algo-live --config ~/trade.json --dry-run     # ничего не покупает, только считает
algo-live --config ~/trade.json --yes         # реальная торговля (осознанно)
```

`--yes` — это «я понимаю, что торгую реальными деньгами». Без него на сервере
(где некому ответить на вопрос) реал не запустится — защита от случайного старта.

**4. Уведомления в Telegram (по желанию).** Чтобы узнавать о важном (рубильник
дневного убытка, невозможность защитить позицию, остановка) не заглядывая в
журнал — заведите бота у `@BotFather`, узнайте свой `chat_id` и задайте две
переменные перед запуском:

```
export TELEGRAM_BOT_TOKEN=123456:ABC...
export TELEGRAM_CHAT_ID=987654321
```

**5. Автозапуск и перезапуск (systemd).** Чтобы раннер сам поднимался при
перезагрузке сервера и после сбоя — в проекте есть готовый шаблон
`live/algo-live.service.example`. Скопируйте его в `/etc/systemd/system/`,
поправьте пути и пользователя, секреты вынесите в `/etc/algo-live.env`, затем:

```
sudo systemctl daemon-reload
sudo systemctl enable --now algo-live
journalctl -u algo-live -f          # смотреть журнал вживую
sudo systemctl stop algo-live       # аккуратно остановить (движок выйдет на тике)
```

Состояние сессии (выставленные SL/TP, базис дневного убытка) сохраняется на диск,
поэтому после перезапуска раннер не «забывает» открытую позицию и не снимает с неё
защиту. Полная справка по полям конфига и кодам выхода — в начале файла
[`live/runner.py`](live/runner.py) и в разделе README «Headless-торговля на VPS».

## Частые вопросы

**Почему стратегия в минусе на синтетических данных?** Так и должно быть:
синтетика — случайное блуждание, на нём заработать нельзя. Она нужна только
чтобы проверить механику, а не доходность.

**Почему ордер исполняется не по той цене, где был сигнал?** Сигнал
рассчитывается по закрытию бара, а исполнение — по открытию следующего
(плюс проскальзывание). Это сделано специально: в реальной торговле вы
не можете купить по цене, которую увидели только после закрытия свечи.
Тестеры, которые так делают, завышают результат («заглядывание в будущее»).

**Хорошие цифры после оптимизации — можно торговать?** Нет. Оптимизатор
подгоняет параметры под историю (переобучение). Прогоните Walk-Forward
Analysis (шаг 3б) — он проверяет параметры на данных, которые оптимизатор
не видел, и показывает, переживёт ли стратегия выход «из пробирки».
