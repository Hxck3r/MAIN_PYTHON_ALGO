## Десктопный «Тестер стратегий» (python desktop_app.py)

Классический вид в духе тестера MT5, быстрые графики на pyqtgraph
(100 000+ свечей без лагов, прореживание автоматическое):

- **Слева** — данные (CSV из MT5 или синтетика), период теста, капитал,
  комиссия, проскальзывание, стратегия, критерий и метод оптимизации.
- **Центр** — график: свечи, маркеры входов/выходов, кривая эквити;
  колесо мыши — зум, перетаскивание — прокрутка, перекрестие — курсор.
- **Снизу вкладки**: «Параметры» (галочка «Опт.» + Старт/Шаг/Стоп, как
  в MT5), «Результаты» (все метрики), «Сделки», «Оптимизация» (таблица
  всех испытаний с сортировкой; двойной клик по строке подставляет
  параметры и запускает бэктест), «Журнал».
- Расчёты идут в фоновых потоках — окно не «замерзает», прогресс
  в статус-баре.

Критерии оптимизации: Net Profit, доходность %, Sharpe, Sortino,
Profit Factor, Win Rate, Recovery Factor, матожидание, Complex Criterion
(комплексный, как в MT5). Методы: полный перебор и генетический алгоритм.

## Два движка — один контракт стратегии

Стратегия — это «картридж»: класс, который вставляется в тестер. Движок не
знает, что внутри стратегии; стратегия не знает, как устроено исполнение.
Есть два движка с **одинаковой моделью исполнения** (вход по открытию
следующего бара, приоритет SL, спред/слиппедж/комиссии, неттинг) — выбирайте
под задачу:

| | Событийный (`BacktestEngine`) | Быстрый (`run_fast_backtest`) |
|---|---|---|
| Базовый класс | `BaseStrategy` (`init` + `next`) | `SignalStrategy` (`compute_signals`) |
| Логика | произвольная, бар за баром | выражается массивами сигналов |
| Скорость (100k баров) | ~0.3 c | ~0.01 c (ядро ~0.6 мс) |
| Зависимость | только numpy/pandas | + `numba` (extras `[fast]`) |
| Когда брать | сложная логика: трейлинг, лимитные/стоп-ордера, частичные закрытия, состояние между барами | одна неттинг-позиция + SL/TP по сигналам; **массовая оптимизация и WFA** |

Результаты обоих движков для сигнальной стратегии **совпадают побитово**
(проверяется в тестах) — быстрый движок не «другая модель», а та же модель
на скомпилированном ядре. Практический приём: пишите стратегию как
`SignalStrategy` (она работает на обоих движках), оптимизируйте/прогоняйте
WFA быстрым движком, а сложную ручную отладку при желании — на событийном.

## Своя стратегия за 3 шага (событийный движок)

**Шаг 1.** Создайте файл `strategies/my_strategy.py` с классом-наследником
`BaseStrategy`. Стратегия — это всегда **класс** (не функция и не скрипт):
движок умеет работать только с наследниками `BaseStrategy`.

```python
from backtester import BaseStrategy, Bar
import numpy as np
import pandas as pd

class MyStrategy(BaseStrategy):
    params = {"period": 20, "sl_pct": 0.02, "tp_pct": 0.05}  # 1. параметры (видны оптимизатору)

    def init(self) -> None:                      # 2. предрасчёт индикаторов (один раз)
        self.sma = pd.Series(self.full_close).rolling(int(self.p["period"])).mean().to_numpy()

    def next(self, bar: Bar) -> None:            # 3. логика на каждом баре
        i = bar.index
        if np.isnan(self.sma[i]):
            return                               # индикатор ещё не прогрелся
        if bar.close > self.sma[i] and not self.position:
            self.buy(stop_loss=bar.close * (1 - self.p["sl_pct"]),
                     take_profit=bar.close * (1 + self.p["tp_pct"]))
        elif bar.close < self.sma[i] and self.position:
            self.close_position()
```

**Шаг 2 — регистрация (обязательно!).** Чтобы стратегия появилась в GUI и в
`main.py`, добавьте её в реестр `strategies/__init__.py` — импорт + строку
в словарь `STRATEGIES` (ключ = имя, видимое в выпадающем списке GUI):

```python
from .my_strategy import MyStrategy

STRATEGIES = {
    "SMA Crossover (пересечение скользящих)": SmaCrossStrategy,
    "Моя стратегия (SMA + SL/TP)": MyStrategy,        # <- добавили
}
```

> Если забыть про реестр — при запуске будет `ModuleNotFoundError` или
> `ImportError`. Имя класса в `__init__.py` должно точно совпадать с именем
> класса в файле стратегии, а сам файл — лежать в папке `strategies/`.

**Шаг 3 — запуск.** `python desktop_app.py` → стратегия в списке слева;
либо в `main.py` подставьте свой класс в `strategy_cls=...`.

### Чек-лист правильной стратегии

- **Тяжёлые расчёты — в `init()`**, а не в `next()` (он вызывается на каждом баре).
- **Индикаторы — векторно** (`rolling`/`ewm`/`np`-операции на всём массиве),
  без Python-циклов по барам: цикл в `init()` пересчитывается на каждой
  комбинации параметров и убивает выигрыш от оптимизации.
- **Индексируйте по `bar.index`**: `self.sma[bar.index]`, `[i-1]` и т.п.
- **Никакого заглядывания в будущее**: индикатор в точке `i` должен
  использовать только бары ≤ `i`. `rolling`/`ewm`/`shift(+k)` это гарантируют.
  Опасно: `shift(-k)`, `center=True`, `bfill`, нормировка по всему ряду
  (`(x-x.mean())/x.std()`) — они подмешивают будущее (его ловит тест в `tests/`).
- **Торгуйте только через API** `self.buy/sell/close_position` — сайзинг
  можно отдать риску: `self.buy(risk_pct=0.01, stop_loss=...)`.

## Быстрая стратегия для numba-движка

Тот же контракт, но логика выражается **массивами сигналов**. Наследуйте
`SignalStrategy` и заполните в `compute_signals()` массивы длины n:
`_sig[i]` (+1 лонг / −1 шорт / 0 — ничего; исполнится на открытии `i+1`),
`_sl[i]` / `_tp[i]` (абсолютные уровни SL/TP, `NaN` — нет), опционально
`_size[i]` / `_risk[i]`. Тот же класс работает и на событийном движке.

```python
import numpy as np, pandas as pd
from backtester.fast_engine import SignalStrategy, run_fast_backtest, assert_no_lookahead

class MySignal(SignalStrategy):
    params = {"period": 20, "sl_pct": 0.02, "tp_pct": 0.05}

    def compute_signals(self) -> None:            # вызывается один раз
        close = pd.Series(self.full_close)
        sma = close.rolling(int(self.p["period"])).mean().to_numpy()
        prices = self.full_close
        # ВЕКТОРНО, без цикла по барам: пробой SMA снизу вверх -> лонг
        prev = (prices[:-1] <= sma[:-1]) & (prices[1:] > sma[1:])
        idx = np.flatnonzero(prev & ~np.isnan(sma[:-1])) + 1
        self._sig[idx] = 1
        self._sl[idx] = prices[idx] * (1 - self.p["sl_pct"])
        self._tp[idx] = prices[idx] * (1 + self.p["tp_pct"])

result = run_fast_backtest(df, MySignal, {"period": 20}, commission_pct=0.0005)
assert_no_lookahead(MySignal, df, {"period": 20})   # проверка причинности сигналов
```

> **Важно про lookahead в сигнальной форме.** Защита в виде «срезов до бара
> `i`» здесь не работает — `compute_signals()` видит весь массив сразу.
> Прогон на событийном движке тоже **не** проверяет причинность (оба движка
> читают одни и те же предрассчитанные сигналы). Поэтому для каждой
> сигнальной стратегии вызывайте `assert_no_lookahead(...)`: она пересчитывает
> сигналы на префиксах данных и ловит зависимость от будущих баров.

> **Готовый индикатор-функция?** Оберните его: посчитайте сигналы в
> `init()` / `compute_signals()` через свою функцию, а торгуйте по
> предрассчитанным массивам. Сам по себе модуль с функцией стратегией не
> является — тестеру нужен класс-наследник `BaseStrategy`/`SignalStrategy`.

## Модель исполнения (важно)

- Симуляция событийная, «бар за баром» — без заглядывания в будущее.
- Рыночный ордер, выставленный на баре `i`, исполняется по **открытию бара `i+1`**
  с учётом проскальзывания.
- Лимитный ордер исполняется при пересечении ценой `limit_price`;
  стоп-ордер (`stop_price` в buy/sell) — при пробое уровня
  (buy-stop вверх, sell-stop вниз; гэп через уровень — по открытию, хуже уровня).
- Спред (`spread_pct`): данные считаются bid-ценами (как в MT5) — любая
  **покупка** (вход в лонг, выкуп шорта, включая SL/TP шорта) исполняется
  по ask = цена × (1 + spread_pct); продажи — по цене графика.
- Плечо (`max_leverage`): ноционал позиции не превышает
  `equity × max_leverage`; избыточный размер урезается (особенно важно при
  `risk_pct`-сайзинге с близким стопом, иначе плечо бесконечно).
  По умолчанию ограничения нет (как раньше).
- SL/TP проверяются внутри бара по high/low; если в одном баре задеты оба —
  консервативно засчитывается Stop-Loss. Гэп через уровень исполняется по
  цене открытия (хуже уровня), как в реальности.
- Позиция — неттинг (одна агрегированная, как в MT5): встречный ордер
  закрывает текущую и открывает остаток в обратную сторону.
- Сайзинг позиции (3 режима, взаимоисключающие аргументы buy/sell):
  - `size=...` — явный объём в единицах актива;
  - `risk_pct=...` + `stop_loss=...` — от риска: объём подбирается так,
    чтобы выход ровно по SL стоил `risk_pct` от текущего эквити
    (гэп через уровень и комиссии могут увеличить фактический убыток);
  - без аргументов — автосайзинг `default_size_pct` (95%) от эквити.

## Walk-Forward Analysis

Реализован в `backtester/walk_forward.py` и интегрирован в GUI (кнопка
«Walk-Forward», вкладка с дашбордом). История режется на скользящие (или
якорные) окна: оптимизация на in-sample участке, прогон лучших параметров
на out-of-sample. OOS-прогоны сшиваются в одну кривую с компаундингом
капитала, считаются метрики устойчивости: **Walk-Forward Efficiency**,
доля прибыльных окон, разброс OOS-доходностей, стабильность параметров.
Параметр `warmup_bars` подаёт в каждый OOS-прогон хвост IS для прогрева
индикаторов (торговля на нём запрещена, эквити и сделки считаются только
внутри OOS) — без него первые бары каждого окна стратегия «слепа».
Подробности — в GUIDE.md, шаг 3б.

## Матричный WFO (WFA Cluster Analysis)

Реализован в `backtester/wfa_matrix.py` и интегрирован в GUI (кнопка
«Матричный WFO», вкладка «Матрица WFO» с тепловой картой). Сами длины
IS/OOS — такие же произвольные параметры, как параметры стратегии: удачная
WFE при IS=180/OOS=45 ничего не значит, если при IS=160/OOS=40 всё
рушится. Матричный WFO прогоняет полный walk-forward для каждой комбинации
длин из двух списков (IS × OOS) и строит матрицу агрегатных метрик. Ищем
**плато (кластер) стабильности** — широкую область соседних ячеек с похоже
хорошими результатами: если оно есть, стратегия устойчива к выбору длин
окон; одинокий яркий пик среди провалов — переподгонка под нарезание.

Сводные числа: средняя WFE по сетке, доля прибыльных ячеек, коэффициент
вариации целевой метрики (чувствительность к длинам окон), и **рекомендация
— центр лучшего плато** (максимум среднего по окрестности 3×3, а не
глобальный пик). Двойной клик по ячейке тепловой карты подставляет её длины
IS/OOS в настройки Walk-Forward.

Производительность (рассчитано на слабый CPU): единый пул процессов на всю
матрицу (история пересылается воркерам один раз, а не на каждую ячейку); в
последовательном режиме — общий кэш IS-оценок между ячейками (совпадающие
IS-срезы не считаются повторно); нежизнеспособные ячейки отсеиваются до
прогона; полные результаты ячеек по умолчанию не хранятся (память).

```python
from backtester import WfaMatrixConfig, run_wfa_matrix

cfg = WfaMatrixConfig.from_ranges(
    df.index[0], df.index[-1],
    is_range=(90, 360, 4), oos_range=(20, 90, 4),   # (min, max, count)
)
res = run_wfa_matrix(df, MyStrategy, cfg, grid={"fast": [5, 10, 15]},
                     metric="sharpe_ratio", target="wfe_pct", n_jobs=0)
print(res)                       # сводка + рекомендованные длины IS/OOS
print(res.matrix("wfe_pct"))     # тепловая карта как DataFrame (IS × OOS)
robust = res.robust_cell()       # центр плато: рекомендуемые длины окон
```

## Монте-Карло

Реализован в `backtester/monte_carlo.py` и интегрирован в GUI (кнопка
«Монте-Карло», вкладка с дашбордом). Сделки бэктеста перемешиваются /
ресэмплируются тысячи раз (перестановка, бутстрэп, блочный бутстрэп;
реинвестирование или фиксированный размер) — из них строятся новые кривые
эквити. На выходе: распределения доходности и просадки (P5…P95, VaR/CVaR),
вероятности достижения цели / превышения лимита просадки / разорения,
серии убытков, защита от переоптимизации (перцентиль исходного бэктеста
в облаке симуляций, p-value прибыльности, ДИ матожидания). Графики: веер
кривых эквити с перцентильными конвертами, гистограммы, CDF доходности.
Подробности — в GUIDE.md, шаг 3в.

## Статистическая защита от переоптимизации

Модуль `backtester/statistics.py` — ответ на вопрос «лучший результат
оптимизации — сигнал или артефакт перебора?»:

- **Deflated Sharpe Ratio** (Bailey & López de Prado): PSR против порога —
  ожидаемого максимума Sharpe среди N испытаний чистого шума. `DSR > 0.95` —
  результат значим даже с учётом числа перебранных комбинаций. **Считается
  автоматически** и печатается в отчётах оптимизации (CLI и GUI) и WFA:
  `n_trials` = число перебранных комбинаций.
- **Плато-выбор параметров** (`select_plateau_params`): вместо argmax по
  сетке — лучшее среднее по окрестности; острые одиночные пики
  (= переобучение) проигрывают устойчивым областям.
- **Permutation-тест** (`permutation_test`): стратегия прогоняется на
  множестве перемешанных копий истории (геометрия баров и распределение
  доходностей сохраняются, порядок разрушается). Малое p-value — стратегия
  эксплуатирует именно временнУю структуру рынка.

```python
from backtester import (
    deflated_sharpe_from_optimization, permutation_test, select_plateau_params,
)

# DSR лучшего результата оптимизации (прогон + дефляция на число испытаний)
print(deflated_sharpe_from_optimization(
    df, MyStrategy, opt_result.best_params, n_trials=len(opt_result.history),
))
print(permutation_test(df, MyStrategy, best_params))     # p-value против шума
params, _ = select_plateau_params(opt_result.history)    # устойчивый оптимум
```

## Машинное обучение (вкладка «🧠 Машинное обучение»)

Пакет `ml/` добавляет профессиональное ML «из коробки», не дублируя движок:
обученная модель становится обычной стратегией `MLStrategy` и прогоняется тем же
бэктестером — поэтому к ней применяются **Walk-Forward, Монте-Карло, PBO и Deflated
Sharpe** без изменений. Поддержаны классические модели (LightGBM / Random Forest /
Gradient Boosting / Logistic Regression) — быстро на CPU и нетребовательно к памяти.

Пайплайн: **данные → признаки → purged walk-forward → out-of-fold вероятности →
бэктест на OOS-сегменте → аппарат робастности**.

- **Признаки** (`ml/features`): стационарные (доходности/отношения, RSI, MACD,
  Боллинджер, ATR, стохастик, объём), **календарные** (час/день недели, циклически)
  и **режимные** (режим волатильности, долгий моментум). Пресеты «Лёгкий / Стандарт /
  Расширенный».
- **Цель** (`ml/features/labeling.py`): направление цены или **тройной барьер**
  (López de Prado, масштаб по волатильности — по умолчанию, экономически осмысленнее).
  Последние `horizon` баров метки отбрасываются — нет заглядывания в будущее.
- **Валидация** (`ml/validation.py`): `PurgedWalkForwardSplit` с **purge + embargo** —
  обучение строго на прошлом, проверка на будущем, зазор против утечки.
- **Обучение** (`ml/trainer.py`): метрики только вне обучения (OOS), балансировка
  классов, калибровка вероятностей, подбор порога (Youden/F1), опциональный
  **подбор гиперпараметров** случайным поиском на той же purged-CV (`ml/tuning.py`).
- **Значимость** (`ml/significance.py`): доверительный интервал AUC (DeLong) и
  **Information Coefficient** (корреляция вероятности с будущей доходностью) — чтобы
  отличить реальный край от случайного.
- **Диагностика данных** (`ml/diagnostics.py`): баланс классов, baseline и тест
  «случайного блуждания» (variance ratio) — видно, дело в модели или в самих данных.

Меры против переобучения — **два слоя**: (1) честная OOS-оценка модели (purged
walk-forward); (2) сделки ML-стратегии прогоняются через Монте-Карло / PBO / DSR
основного приложения. **Вердикт-светофор** опирается не на голый AUC (на финансах
0.50–0.55 — норма), а на **статистическую значимость** (нижняя граница CI > 0.5 или
значимый IC) и устойчивость по фолдам: слабый, но значимый и стабильный край — это
«есть преимущество», а высокий, но незначимый AUC — случайность.

Рабочий цикл в GUI: открыть вкладку **«🧠 Машинное обучение»** → выбрать пресет/цель/
модель → **«Обучить»** (фоновый поток, прогресс и отмена) → посмотреть OOS-метрики,
важность признаков и вердикт → **«→ В стратегию»** (подставит модель в `MLStrategy` и
прогонит бэктест) → запустить на нём Монте-Карло и PBO. Модель сохраняется артефактом
`RunBundle` (`.joblib` + `.json`-сводка) с отпечатком данных для воспроизводимости;
кнопки **«Сохранить» / «Загрузить»**. Матрица признаков кешируется по отпечатку данных
и настройкам — повторное обучение не пересчитывает индикаторы (важно на слабом ПК).

> Зависимости ML (`scikit-learn`, `lightgbm`, `joblib`) ставятся через
> `pip install -e ".[ml]"` и подгружаются **лениво** (только при открытии вкладки),
> поэтому старт приложения не тяжелеет. Без них приложение работает как прежде, а
> вкладка показывает подсказку по установке.

## Торговля на бирже (окно «Торговля», демо/реал)

Кнопка **«🟢 Торговля (демо / реал)»** в панели тестера открывает **отдельное окно**
live-торговли на бирже **BingX** (CEX) или **Lighter** (DEX) — линейные
перпетуалы — через единый адаптер `ccxt` (пакет [`live/`](live/)). Тестер при этом
не засоряется.

В окне:
- **Подключение** — биржа, режим **Демо/тестнет** или **РЕАЛ ⚠** и ключи API
  (хранятся вне репозитория в `~/.config/main_python_algo/`, права `0600`), плечо
  и режим маржи. Поля ключей зависят от биржи: у CEX это **API Key + Secret**, у
  DEX **Lighter** — **приватный ключ API** и индексы аккаунта (**Account Index /
  API Key Index** из приложения Lighter). Кнопка **«Проверить подключение»** грузит
  баланс и список символов.
- **Стратегия из тестера** — текущая стратегия и её параметры переносятся
  автоматически (можно выбрать другую и отредактировать в той же таблице параметров).
- **Символ** — поиск по перпетуалам (USDT у BingX, USDC у Lighter); при выборе
  появляется **график цены** (те же быстрые свечи finplot), обновляемый в реальном времени.
- **Размер позиции** — фиксированный ноционал или % от баланса; плюс
  **«Сухой прогон»** — цикл работает, но ордера не отправляются (безопасная проверка).
- **Исполнение** — лимитные (мейкерские) входы, мейкерский тейк-профит и
  **максимальное проскальзывание**: если к моменту исполнения рыночного входа цена
  ушла против него дальше заданного процента, ордер не выставляется (вход
  пропускается). Закрытия и защитные ордера проскальзыванием не блокируются.
- **Старт/Стоп** — движок ([`live.engine`](live/engine.py)) на каждом **закрытом баре**
  пересобирает стратегию над окном истории и через `LiveBroker`
  ([`live/broker.py`](live/broker.py)) исполняет её сигналы реальными ордерами; SL/TP
  выставляются биржевыми reduce-only стоп-ордерами. Те же стратегии, что и в тестере, —
  без единой правки (общий контракт «стратегия ↔ брокер»).

> Зависимости торговли (`ccxt`) ставятся через `pip install -e ".[live]"` и
> подгружаются **лениво**. Без них приложение работает как прежде, а окно торговли
> показывает подсказку по установке.
>
> **BingX (CEX):** демо-фьючерсы (VST) через testnet (`open-api-vst.bingx.com`);
> реальные ордера на USDT-перпетуалы выставляются надёжно.
> **Lighter (DEX):** перпетуалы с расчётом в USDC. Авторизация НЕ через
> публичный/секретный ключ: создайте **ключ API** в приложении Lighter и введите
> его **приватный ключ API** + индексы (**Account Index / API Key Index**, целые
> числа). Сырой приватный ключ кошелька вводить НЕ нужно — это безопаснее (ключ
> API можно отозвать, он не даёт доступа к самому кошельку). Дополнительно нужна
> **нативная библиотека-подписант**: скачайте `.so` для своей ОС из
> [elliottech/lighter-python](https://github.com/elliottech/lighter-python/tree/main/lighter/signers)
> и укажите путь к нему в поле «Lighter Signer (.so)». Демо — отдельный публичный
> тестнет (ключи и индексы основной сети там не работают). Биржевые стоп/тейк-
> ордера у DEX через ccxt могут поддерживаться ограниченно.

## Headless-торговля на VPS (`algo-live`) и уведомления

Для автономной работы на сервере без графики есть консольный раннер
[`live/runner.py`](live/runner.py) — он запускает **тот же** движок
([`live.engine`](live/engine.py)), что и окно «Торговля», но управляется
JSON-конфигом, пишет журнал в `stdout` (его подхватывает `journald`), корректно
останавливается по `SIGINT`/`SIGTERM` и переживает рестарты (состояние сессии —
SL/TP, базис дневного убытка — сохраняется в `~/.config/main_python_algo/`).

```bash
pip install -e ".[live]"                       # ставит ccxt
cp live/trade.example.json ~/trade.json        # отредактируйте под себя
algo-live --config ~/trade.json --dry-run      # 1) сухой прогон (без ордеров)
algo-live --config ~/trade.json --yes          # 2) реальная торговля (осознанно)
```

**Конфиг** ([`live/trade.example.json`](live/trade.example.json)) — биржа, режим
(`demo`/`real`), символ, таймфрейм, стратегия (имя из реестра или имя класса) и её
параметры, плечо, sizing/execution/risk. Поле `execution.require_protective`
(по умолчанию `true`) важно для **Lighter**: если биржевой **стоп-лосс не встал**,
раннер аварийно закроет позицию и остановится, а не оставит её без защиты.

**Ключи в конфиг НЕ кладутся** (секреты не на диске в открытом виде). Раннер берёт
их так:
1. из переменных окружения `ALGO_CRED_<ПОЛЕ>` в верхнем регистре, например
   `ALGO_CRED_PRIVATE_KEY`, `ALGO_CRED_ACCOUNT_INDEX`, `ALGO_CRED_API_KEY_INDEX`
   (для CEX — `ALGO_CRED_API_KEY`, `ALGO_CRED_SECRET`) — удобно для systemd
   `EnvironmentFile`;
2. иначе из общего хранилища ключей, которое заполняет GUI.

**Безопасность реала:** при `mode:"real"` без `dry_run` старт требует явного
подтверждения — флаг `--yes` (для неинтерактивного systemd) либо ответ в терминале.
Без подтверждения торговля реальными деньгами не начнётся. Коды возврата для
`Restart=` в systemd: `0` — чистый стоп, `1` — сбой цикла, `2` — ошибка конфига,
`3` — нет подтверждения реала, `4` — ошибка подключения.

**Уведомления в Telegram** (опционально, без сторонних зависимостей) включаются
двумя переменными окружения — раннер шлёт в чат старт/стоп, ошибки и все
**фатальные/риск-события** (рубильник дневного убытка, невозможность защитить
позицию), чтобы вы узнали о них, не глядя в журнал:

```bash
export TELEGRAM_BOT_TOKEN=123456:ABC...     # токен бота от @BotFather
export TELEGRAM_CHAT_ID=987654321           # ваш chat_id
```

**systemd:** готовый юнит — [`live/algo-live.service.example`](live/algo-live.service.example)
(`Restart=always`, `EnvironmentFile`, остановка по `SIGTERM`). Кратко:

```bash
sudo cp live/algo-live.service.example /etc/systemd/system/algo-live.service
sudoedit /etc/systemd/system/algo-live.service   # пути, User, --config
sudoedit /etc/algo-live.env                       # секреты (права 0600)
sudo systemctl daemon-reload && sudo systemctl enable --now algo-live
journalctl -u algo-live -f                         # живой журнал
```

> Сначала обкатайте конфиг на **демо/тестнете** и в `--dry-run`, и лишь затем
> переходите на реал малым размером. Для Lighter помните: демо — отдельный тестнет
> с отдельными ключами.

## Тиковые данные, футпринт и ордерфлоу

Пакет `marketdata` добавляет к свечным данным второй, независимый слой:
поштучные публичные сделки (ticks) трёх бирж и их агрегация в футпринт.
Опциональные зависимости: `pip install -e ".[marketdata]"` (CCXT + PyArrow;
PyArrow нужен и GUI, чтобы читать Parquet-партиции). Инструмент по умолчанию —
линейный перпетуал `BTC/USDT:USDT`.

### Bulk-архивы бирж: годы тиков за минуты

Для массовой истории постраничный CCXT не годится (см. ограничения ниже),
поэтому основной путь — собственные архивы бирж. Один день BTC-перпетуала — это
1.2–1.8 млн сделок на биржу, и они скачиваются целыми дневными файлами, а не
страницами по 1000 сделок:

```bash
# Тики трёх бирж за месяц + футпринт Parquet + свечи для бэктеста
algo-trades archive -e binance bybit okx \
    --since 2024-01-01 --until 2024-02-01 \
    --data-dir marketdata_store --footprint --price-step 10 --candles 1m

# Что будет скачано, ничего не скачивая
algo-trades archive -e bybit --since 2024-01-01 --until 2024-02-01 --dry-run

# Загруженное можно пересобрать с другим шагом цены/таймфреймом
algo-trades footprint --price-step 25 --timeframe 5min --out footprint.parquet
```

Что важно знать про эти архивы (всё это проверено на живых файлах и закреплено
тестами `tests/test_marketdata_archives.py`):

* **Покрытие.** Binance USD-M (`data/futures/um/daily/...`) и Bybit linear дают
  полные дни по всем инструментам; OKX (`traderecords`) — тоже, но **диапазон
  суток у OKX в UTC+8**: файл `20240102` покрывает UTC `[01-01 16:00, 01-02 16:00)`.
  Загрузчик берёт поэтому на один файл больше и обрезает его по окну, иначе
  граничные сутки посчитались бы дважды.
* **Единицы.** Binance/Bybit отдают размер в базовом активе, OKX — в контрактах:
  размер умножается на `ctVal × ctMult` из метаданных инструмента (для
  `BTC-USDT-SWAP` это 0.01 BTC). Всё в сторе — в BTC, как и у CCXT-загрузчика.
* **Сторона.** У Binance в `aggTrades`/`trades` есть только `isBuyerMaker`, то
  есть флаг читается инвертированно; Bybit и OKX отдают сторону агрессора прямо.
* **`aggTrades` против `trades`.** Это два представления одной ленты: смешивать
  их в одном сторе нельзя (те же сделки посчитались бы дважды), и загрузчик это
  запрещает. По умолчанию — `aggTrades`: та же агрессия и объём, но файлов и
  строк втрое меньше. Сделки из `aggTrades` помечаются префиксом `agg:` в
  `trade_id`, поэтому два потока не склеятся и в дедупликации.
* **Свечи.** Bulk-свечи публикует только Binance (`klines`, включая
  `taker_buy_volume`), поэтому интервал свечей и таймфрейм футпринта обязаны
  совпадать — иначе признаки не совместятся с барами тестера, и это проверяется
  до начала загрузки. У Bybit/OKX архива свечей нет.
* **Свежесть.** Архивы публикуются с задержкой (обычно до T-1), поэтому верхняя
  граница диапазона не включается: `--until` — день, который уже есть.
* **Возобновляемость.** Скачанное лежит в каноническом сторе теми же
  Parquet-партициями по дням (`canonical/exchange=/symbol=/date=`), а
  `archives_state.json` помнит, какие файлы завершены. Повторный запуск той же
  команды докачивает только недостающее; `--force` перекачивает заново.

### Консоль `algo-trades`

```bash
# 1) Загрузка истории сделок с трёх бирж сразу (перекрытие/дедупликация из коробки)
algo-trades download -e binance okx bybit \
    --since 2024-01-01 --until 2024-02-01 --limit 1000

# 2) Футпринт: отдельные колонки по биржам + combined_* (общий, без двойного счёта)
algo-trades footprint --price-step 10 --timeframe 1min --out footprint.parquet

# 3) Причинные признаки по барам для стратегий (и для колонок-фич тестера)
algo-trades features --price-step 10 --window 20 --out features.csv

# 4) Что уже скачано: партиции, чекпойнты, последние проблемы качества данных
algo-trades status
```

То же самое делает скрипт `fetch_ticks.py` в корне репозитория — это тонкая
обёртка над `marketdata/archives.py` для тех, кто не ставил пакет.

В GUI тиковые архивы качает кнопка **«Скачать тиковые данные (архивы)...»**:
биржи галочками, инструмент, диапазон дат, таймфрейм и шаг цены, число потоков,
а по окончании — «Открыть в тестере», то есть свечи и футпринт сразу становятся
данными бэктеста. Прогресс, журнал и кнопку «Остановить» ведёт фоновый поток
`ArchiveDownloadWorker` (тот же код, что и у консоли).

Время принимается как epoch milliseconds, ISO-8601 с оффсетом или как голая дата
`YYYY-MM-DD` (её консоль трактует как UTC — на командной строке другого оффсета
нет). `--price-step` обязателен: шаг цены, зависящий от инструмента, нельзя
угадать, и по умолчанию получилась бы бесполезная сетка «один уровень на бар».

### Что именно делается с данными

* **Схема сделки** (`marketdata/core.py`): `timestamp, exchange, symbol,
  trade_id, source_identity, price, quantity, side, contract_type,
  quantity_unit`. `side` — это сторона **агрессора** (тейкера): buy значит
  покупка по рынку. Флаг биржи `isBuyerMaker` читается инвертированно.
* **Единицы объёма.** Всё хранится в BTC (базовый актив). Биржи котируют разное
  число базового актива в контракте (Binance/Bybit — 1 BTC, OKX — 0.01 BTC),
  поэтому `contract_size` берётся из метаданных инструмента биржи и попадает в
  отчёт; при повторной загрузке с другим `contract_size` появляется предупреждение
  и запись в манифесте, потому что смешивать две единицы в одном сторе нельзя.
  `--quantity-source base` отключает пересчёт, `--contract-size` задаёт значение
  вручную. Сырые поля `qty/size/sz` без `contract_size` отклоняются: назвать их
  BTC честно нельзя.
* **Время.** Timezone-naive timestamp не принимается: угадывание зоны сдвинуло бы
  сделки в чужой бар и испортило футпринт. Используется первый валидный из
  `timestamp → datetime → info.timestamp → info.ts → info.T`.
* **Хранение** (`store.py`): канонические сделки — Parquet-партиции
  `exchange=/symbol=/date=`, каждая страница ответа биржи — ещё и сырой JSONL
  (`raw/`) до нормализации, чтобы спорную строку можно было разобрать заново.
  Запись партиции идёт через временный файл (сбой не портит уже скачанную
  историю), дубли отсекаются по стабильному `trade_id`.
* **Футпринт** (`core.py`): цена раскладывается по бакетам целочисленной
  арифметикой через `Decimal` (иначе `0.3 / 0.1` попадает в бакет `0.2`).
  `aggregate_footprint` даёт независимые колонки `<биржа>_buy_qty/sell_qty/delta/...`
  и `combined_*`, а также флаги `<биржа>_covered`: `combined_*` — это сумма
  бирж, а `*_covered` показывает, какие биржи в этой ячейке вообще были, чтобы
  нулевую активность не путать с отсутствием данных.
* **Признаки** (`features.py`): `cumulative_delta`, `rolling_delta`,
  `rolling_volume`, `delta_zscore`, `buy_sell_ratio`, `volume_imbalance`. Все
  скользящие считаются только по текущему и прошлым барам; флаги покрытия
  агрегируются логическим ИЛИ и никогда не суммируются как объём.
* **Структура ячеек** (`features.cell_order_flow_features`): то, что видно
  только внутри бара — `poc_price/poc_volume/poc_share` (цена и доля
  максимального объёма), `poc_migration` (дрейф POC от бара к бару),
  `value_area_high/low/share` (растущая от POC зона ~70 % объёма, как на
  профиле рынка), `buy_imbalance_levels`/`sell_imbalance_levels` (диагональный
  имбаланс: агрессивный объём ячейки против объёма в тике от неё),
  `imbalance_stack` (длина непрерывной серии имбалансов со знаком стороны),
  `imbalance_skew`, `absorption_price/volume/signal` (тяжёлая ячейка с почти
  нулевой дельтой — агрессию встретил лимит: − дельта → +1, покупателей
  встретили оффера → −1), `delta_divergence` (новый минимум при положительной
  дельте → +1, новый максимум при отрицательной → −1), `bar_high_cell/low_cell`,
  `bar_vwap`, `bar_range_ticks`. Каждая величина описывает **закрытый** бар:
  ячейки бара известны только к его закрытию, и признак никогда не заглядывает
  вперёд (проверено тестом «префикс прогона совпадает с полным»).
* **Стратегии.** `BacktestEngine(..., market_features=..., footprint=...)`
  принимает признаки (и по барам, и сам футпринт для отрисовки); в `init()`
  доступны `self.full_features` / `self.feature("rolling_delta")`, в `next()` —
  `self.features` (только до текущего бара). Примеры:
  `strategies/footprint_delta.py` (дельтовые тоталы) и
  `strategies/footprint_imbalance.py` («Footprint imbalance + absorption»:
  имбаланс + z-оценка дельты + вето абсорбции, стоп/тейк по ATR; без
  футпринт-признаков стратегия падает с внятной ошибкой, а не торгует наугад).
  В GUI футпринт рисуется тепловой картой под свечами (кнопка загрузки тиковых
  данных в главном окне).

### Ограничения источников (честно)

Публичные CCXT endpoints не являются bulk-архивом многолетней истории: глубина,
лимиты и пагинация зависят от биржи, а `fetch_trades(symbol, since, limit)`
пагинирует **только по времени**. Если в одну миллисекунду сделок больше, чем
помещается в страницу, курсор по времени не позволяет добрать остаток. Загрузчик
это распознаёт и по умолчанию **предупреждает** и пишет проблему в манифест
(`incomplete_buckets`), продолжая с записи после этой миллисекунды; с
`--strict-pagination` вместо этого падает с `RuntimeError`. Молча неполных данных
не бывает: без cursor/ID-API полноту гарантировать нельзя. Для массовой истории
используйте `algo-trades archive` (см. выше) — там неполнота дня видна сразу:
недоступный файл попадает в отчёт, а не в тихую дыру в данных.

Загрузка возобновляемая: чекпойнт (`checkpoint.json`) хранит следующий `since`
по каждой паре биржа/символ, поэтому повторный запуск той же команды продолжает
с места остановки, а не начинает заново. Если биржа даёт стабильный ID/sequence,
он сохраняется и служит ключом дедупликации; для строк без ID ключом становится
хэш содержимого вместе с sequence, поэтому два одинаковых print с разными
sequence остаются двумя сделками, а точный повтор строки отбрасывается.

## Дорожная карта

Архитектура рассчитана на расширение без переписывания ядра.

**Уже реализовано:**

- ✅ PBO/CSCV (probability of backtest overfitting) — `backtester/pbo.py`.
- ✅ Реестр прогонов (отпечаток данных + OOS-метрики, гигиена селекционного
  смещения) — `ml/registry.py`.
- ✅ ML «из коробки» уровня AFML: тройной барьер, мета-лейблинг, fracdiff, веса
  уникальности, purged walk-forward + CPCV, честный OOS с издержками — пакет `ml/`.
- ✅ Headless-раннер live-торговли для VPS (`algo-live`) — JSON-конфиг, ключи из
  env/хранилища, Telegram-уведомления, systemd, корректная остановка по сигналам.
- ✅ Тиковый слой `marketdata`: загрузка публичных сделок binance/okx/bybit,
  Parquet-хранилище с сырым архивом и чекпойнтами, футпринт (по биржам и общий),
  причинные order-flow признаки, стратегия-пример и теплокарта в GUI,
  консоль `algo-trades`.
- ✅ Native bulk-архивы бирж (`marketdata/archives.py`): полные дневные файлы
  Binance Vision, Bybit и OKX, возобновляемая докачка в тот же канонический
  стор, сборка футпринта Parquet и свечей Binance, консоль `algo-trades archive`,
  скрипт `fetch_ticks.py` и окно «Тиковые данные» в GUI.
- ✅ Признаки структуры футпринта (POC, value area, диагональный имбаланс,
  абсорбция, дельта-дивергенция) и стратегия «Footprint imbalance + absorption».

**В планах:**

- Прогон ордерфлоу-стратегий по длинному диапазону архивов (WFA/оптимизация на
  годах тиков) — сейчас параметры подбираются на отдельных днях, а на одном дне
  «следование за агрессией» и «возврат к среднему» статистически неразличимы.
- Optuna как альтернативный `BaseOptimizer` (сейчас — Grid + Genetic + случайный
  поиск гиперпараметров ML).
- Спецификация инструмента (tick size/value, лоты, swap/overnight) для
  форекс/фьючерсов — сейчас издержки процентные.
- Forward / paper-харнесс: проигрывание новых баров на живых данных перед
  реальным капиталом (финальное звено методологии тестирования).
